# Contributing

Thanks for helping improve threats.top. This project publishes threat
intelligence that people make decisions with, so correctness and provenance
matter more than feature count.

## Ground rules

- **`main` is protected.** Every change, including data refreshes, arrives
  through a pull request with required checks. There are no bypass actors.
- **No demo data.** Every value on the site comes from a declared source.
  Placeholder rows, seeded tenants, and sample statistics are rejected by the
  validator and by review.
- **Zero runtime dependencies.** Python standard library only; plain HTML, CSS,
  and ES modules with no framework or build step. A pull request that adds a
  dependency needs a strong justification and will usually be declined.
- **Data is the database.** `data/*.json` is generated by collectors and
  committed. Do not hand-edit generated feeds; the only supported manual write
  path is `data/manual.json` followed by regeneration.
- **One concern per pull request.** Separate code, data, and documentation
  changes unless they are the same change.

## Development setup

Requirements: Python 3.12, Node.js 22 or newer, git.

```bash
python3 scripts/dev.py test                  # normalisation, feed validation, Python and Node tests
python3 scripts/dev.py validate              # validate every data/*.json without the git regression check
python3 scripts/dev.py sync --feed auto      # collect sources that are due
python3 scripts/dev.py serve --port 8080     # serve the site locally
```

The full check suite that CI runs:

```bash
python3 -m unittest discover -s scripts/tests -t scripts
node --test assets worker
python3 scripts/validate_feeds.py --against HEAD
```

## Pull requests

1. Branch from `main`: `feat/...`, `fix/...`, `chore/...`, `docs/...`, or
   `data/...`.
2. Use a conventional commit subject (`feat(cves): ...`, `fix(map): ...`).
3. Fill in the pull request template, including the test plan you actually ran.
4. Wait for **Feed data**, **Unit tests**, and **Python tests** to pass. The
   SonarCloud check must also pass; findings must be fixed rather than muted.
5. Squash merge. History is linear.

## Adding or changing a data source

- Add the collector under `scripts/`, using the shared helpers in
  `scripts/feed_io.py`.
- Declare its cadence, criticality, and feeds in `scripts/status.py`; the
  scheduler uses that table.
- Register its shape in `FEED_SPECS` in `scripts/validate_feeds.py` and add
  tests for the normalisation.
- Regenerate `docs/CONTRACT.md` with
  `python3 scripts/validate_feeds.py --print-contract`.
- Document the source, its terms, cadence, and what is dropped during
  normalisation in `README.md`.
- Never publish upstream data that its licence forbids republishing, and never
  add a keyed source without a documented secret path through Actions.

## Frontend changes

- Escape every upstream string with `esc()`; never build a URL from data without
  an `http(s)` check; keep defanged indicators unclickable.
- Meet WCAG 2.2 AA as described in [ACCESSIBILITY.md](ACCESSIBILITY.md).
- Respect `prefers-reduced-motion`; animation must never be required to read
  data.
- Test at 500 px and 1440 px widths, keyboard-only, and with a screen reader for
  new interaction patterns.
